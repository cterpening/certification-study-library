# AI-103: evaluate a maintenance assistant locally

Allow 45–60 minutes. Use this starter for the retrieval and action-contract portions of Lab 8 in the [AI-103 guide](../../guides/AI-103-developing-ai-apps-and-agents-on-azure.md). [Download or clone the starter files](https://github.com/cterpening/certification-study-library/tree/main/labs/ai-103). Python 3.10 or later is sufficient; the exercise calls no Azure service.

## Predict the retrieval results

Inspect `retrieval-cases.json` before `maintenance.py`. Labels identify relevant and authorized documents independently of the retrieved set. Document IDs are synthetic; `SECRET-DOC` contains no secret. Hand-calculate these outcomes:

| Case | Precision | Recall | Decision to investigate |
|---|---|---|---|
| D1, D3, D4 returned; D1, D2 relevant | 1/3 | 1/2 | D2 is missing; unrelated evidence dilutes context |
| D1, D1, D2 returned | 1 | 1 | Set-based scoring counts each ID once |
| No results; D1 relevant | 0 | 0 | Abstain and investigate retrieval |
| No relevant answer exists in the corpus | 0 | Undefined (`null`) | Abstain; do not call recall 100% |
| D1 and a restricted document returned | 1/2 | 1 | Access breach blocks use despite perfect recall |

The program records unauthorized IDs **before** filtering, so a leak cannot disappear from the evaluation. `eligible_context` and `abstain` use known relevance labels in this offline exercise. They are oracle outputs for the fixture, not a production relevance classifier or a grounded-answer guarantee. In a real application, authorization belongs in the data boundary; labels used for retrospective scoring are generally unavailable at query time.

## Follow the write across the boundary

The trusted test request concerns asset `P-104`. Creating a proposal makes no destination record. An authorized supervisor must approve its exact operation ID, asset and description. Caller access is checked separately. Try these changes in a copy, predicting each result first:

1. Submit before approval: reject with no write.
2. Approve a proposal, then change its description to close an order: reject the changed action.
3. Substitute `P-140` for `P-104`: reject even if that proposal has approval. The expected asset must come from independently validated request context, not a second model-supplied field.
4. Use a caller without asset access: reject despite approval.
5. Replay the same approved operation: return the existing record; exactly one destination record exists.
6. Lose the response after the write: the client initially has an unknown outcome. Look up the original operation, observe its record, and replay only that operation. Do not invent a new key to bypass uncertainty.
7. Reuse an existing operation ID for different, newly approved content: reject the collision and preserve the original record.

`WorkOrders` is an in-memory, single-process model with trusted identity strings. It does not authenticate people, persist data across restarts, enforce concurrent uniqueness, expire/revoke approvals, or implement a real service's retry contract. These omissions are discussion points for the architecture review, not guarantees the learner can transfer to Azure.
